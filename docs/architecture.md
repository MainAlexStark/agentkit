# Архитектура agentkit

## Два слоя

```
┌──────────────────────── проект (agentkit new) ────────────────────────┐
│ app/domain: prompt.md · tools.py · hooks.py · rules()                 │
│ app/skills · mcp.json · evals/ · deploy/*.env                         │
└───────────────────────────────▲───────────────────────────────────────┘
                                │ Domain
┌───────────────────────────────┴──────────── agentkit ─────────────────┐
│ server/   AgentService · build_app (API + веб-чат) · Auth · Settings  │
│ runs      RunManager (фон, SSE, один прогон на сессию) ── bus (Redis) │
│ scheduler cron из базы                                                │
│ agent     цикл ── llm/router ── openai_compat (OpenRouter, Yandex…)   │
│            │  ├── tools/registry ── builtin · domain · mcp            │
│            │  ├── permissions · hooks                                 │
│            │  ├── context (промпт, сжатие, обрезка) · skills          │
│            │  └── subagents (task → дочерний Agent)                   │
│ oauth     вход в MCP-серверы · attachments  файлы и картинки        │
│ projects  инструкции, файлы, память · devices + bridge.py  компьютер  │
│ sandbox   run_python / run_bash: контейнер на разговор · egress       │
│ store     SQLStore: SQLite / PostgreSQL                               │
│ evals · tracing · cli                                                 │
└───────────────────────────────────────────────────────────────────────┘
```

Правило границы: всё, что одинаково у любого агента, — в ядре; проект знает только свою предметную область. Улучшение ядра доезжает до всех проектов обновлением `vendor/agentkit` (`agentkit vendor`).

## Прогон

1. `POST /api/sessions/{id}/messages` → `RunManager.start` → фоновая задача → сразу `run_id`.
2. `Agent.run`: истекают висящие подтверждения → хук `user_prompt_submit` → сообщение в базу → `_loop`.
3. Шаг цикла: история (последняя сводка + хвост) → системный промпт → при переполнении сжатие → запрос к модели (стрим) → assistant в базу.
4. Нет вызовов → хук `stop` (может вернуть агента к работе) → `done`.
5. Есть вызовы → пачки: подряд идущие `parallel_ok` — одновременно. На каждый: есть ли инструмент → загружен ли (отложенный) → валидные ли аргументы → `pre_tool_use` → права → выполнение / отказ / карточка.
6. Есть карточки → прогон завершается со статусом `waiting_approval`. Решение человека (`POST /api/approvals/{id}`) — **новый прогон**: выполнить или отклонить, записать результат, и когда решены все карточки шага — продолжить цикл.

Почему подтверждение не ждёт в памяти: человек ответит через час с телефона, сервис за это время могут перезапустить. Состояние ожидания — строки в `ak_approvals`, а не корутина.

## События

Всё, что делает агент, — `Event` (`events.py`). Они пишутся в `ak_events` (кроме дельт текста), раздаются подписчикам SSE, уходят трейсерам. UI, evals и трейсы читают один и тот же поток. Курсор — `seq`; переподключение отдаёт пропущенное из базы и снимок недописанного текста.

## Права

Решение принимает код, а не промпт (`permissions.py`, порядок — в docstring модуля). Источники: режим сессии, правила из окружения, свойства инструмента (`read_only`, `destructive`, `needs_approval`), хук `pre_tool_use`. Субагент не может спросить человека: «спросить» для него — отказ, задача возвращается главному.

## Контекст

Промпт — слоями, стабильное первым: правила ядра → промпт агента → правила хоста → skills → инструкции MCP → отложенные инструменты → окружение (дата без времени) → память. Сжатие режет только перед сообщением пользователя (пары вызов-результат не рвутся), сводку пишет модель роли small, исходная история остаётся в базе.

## Хранилище

`Store` — интерфейс; `SQLStore` — SQLAlchemy Core, таблицы `ak_*`, схема создаётся сама. Для встраивания в Django-проект можно реализовать `Store` поверх ORM хоста. Миграции (Alembic) — когда схема начнёт меняться у развёрнутых сервисов.

## Развёртывание

Стандарт MCP-серверов: сеть `mcp-network`, общий Caddy в `/opt/infrastructure`, блок по маркерам, секреты один раз, `./deploy.sh update` с автооткатом. Отличие — `flush_interval -1` в Caddy для SSE. Рядом с агентом поднимается Redis (только внутренняя сеть), по умолчанию 2 процесса uvicorn.

## Несколько процессов — `bus.py`

Всё долговременное — в базе (сообщения, события, подтверждения, очередь входящих, OAuth-токены), поэтому любой процесс может обслужить любой запрос. Шина (Redis; в одном процессе — `LocalBus` в памяти) нужна для того, чего в базе нет:

| Что | Как |
|---|---|
| «В сессии идёт прогон» | ключ `ak:run:<сессия>` с TTL 30 с, процесс продлевает его каждые 10 с; умер — ключ истёк сам |
| Живые события и куски текста | канал `ak:ev:<сессия>`; недописанный текст шага — `ak:partial:<сессия>` для подписавшихся посреди ответа |
| Отмена прогона в другом процессе | рассылка `{"cmd":"cancel"}`; владелец прогона ставит флаг отмены |
| «Перечитай MCP» после OAuth | рассылка `{"cmd":"reload"}` всем процессам |
| Обновление OAuth-токена | блокировка `ak:lock:oauth:<сервер>`: refresh ротируется, два одновременных обновления оставили бы процесс без токена |

Запуск по расписанию и решение по карточке защищены атомарным UPDATE в базе (`claim_schedule`, `claim_approval`), а не шиной: так они верны и без Redis.

## Сообщения на ходу

Если агент занят, новое сообщение ложится в `ak_inbox`. Цикл забирает очередь в начале каждого шага — там, где все вызовы предыдущего шага уже закрыты результатами, — и перед тем как закончить. Если прогон закончился раньше, чем сообщение легло в очередь, сервис запускает новый прогон сам (`RunManager.on_idle`). В UI такой пузырь помечен «агент прочтёт после текущего шага», пока не придёт событие `user_message`.

## Вложения — `attachments.py`

Файл — в `uploads/` рабочей папки сессии; в истории — только ссылка `{"type": "file", "path": …}`. Перед запросом к модели ссылка разворачивается: картинка — `image_url` (для моделей со зрением; большие уменьшены заранее), текст и извлечённый при загрузке текст PDF/DOCX/XLSX — в сообщение, длинное — началом и подсказкой `read_file`. Base64 в базе не хранится.

## OAuth для MCP — `oauth.py`

Порт `pkg/oauthclient` из OpenSeller. Admin жмёт «Подключить» → поиск метаданных → регистрация клиента (DCR) → экран согласия MCP-сервера → `/oauth/callback` → токены в `ak_kv` → все процессы перечитывают MCP. Пароль от MCP-сервера агент не видит. Токен общий на сервер; личные токены каждого пользователя — следующий шаг, когда появится многопользовательский сценарий (магазин у каждого свой).

## Решения

| Решение | Почему |
|---|---|
| Python, FastAPI | EI_doc и большинство будущих агентов на Python; лучшая экосистема LLM. В Go-проекты агент встраивается сервисом по HTTP |
| Свой клиент OpenAI-совместимого API вместо SDK | у провайдеров «совместимость» неполная: reasoning, cost, cache_control, формат модели Яндекса — отличия видны полями конфига |
| Свой MCP-клиент вместо SDK | SDK 1.x → 2.x поменял API целиком, а нужна малая часть протокола |
| История в формате OpenAI | один формат для всех провайдеров, смена модели без миграции |
| Ядро в `vendor/` нового проекта | сборка на VPS не требует доступа к приватному репозиторию; обновление — одна команда |
| Своя система пользователей не встроена | у каждого продукта она уже есть; агент получает пользователя от хоста (сервисный токен + заголовки) |

## Проекты, компьютер, песочница

Ядро о них не знает напрямую: агент спрашивает у **поставщиков контекста** (`Agent.context_providers`) текст для промпта и какие инструменты спрятать на этом шаге (`TurnContext`). Проект подмешивает инструкции, память и файлы (или их оглавление); компьютер — какие папки открыты. Если компьютер не подключён или разговор не в проекте, их инструменты модели не показываются вовсе.

**Мост** (`bridge.py`) запускает человек у себя: он ходит на `/api/bridge/poll` (длинный опрос до 25 с) и получает команды из очереди шины (`Bus.push/pop`, в проде — Redis-списки), ответ возвращает в `/api/bridge/result`. Ключ ответа включает id устройства: чужой мост не подсунет результат. Какие папки открыты и разрешены ли команды, решает только мост — сервер не может расширить доступ.

**Компьютер агента** (`agentkit.sandbox`) — `run_python` / `run_bash` вне процесса сервиса. Сервер песочницы — единственный, кто держит `docker.sock`; на каждый разговор он создаёт свой контейнер (`ak-sb-<сессия>`): uid 1000, `cap_drop: ALL`, только чтение корня, `--init`, лимиты памяти/CPU/процессов, смонтирована только папка этого разговора (`/work`). Контейнер живёт, пока разговор активен (фоновые задачи `background=true`, логи в `.jobs/`), и удаляется после простоя (`SANDBOX_IMAGE`, `SANDBOX_IDLE_MINUTES`); пакеты `pip install` ставятся в `/work/.home` и переживают пересоздание. Сеть контейнеров `agent-sandbox-net` — без выхода наружу и без сервиса агента и базы; единственный путь в интернет — прокси **egress** (`agentkit.egress`): домены из `AGENT_SANDBOX_EGRESS`, внутренние адреса запрещены всегда, IP проверяется после резолва и соединение идёт на тот же IP (без DNS-rebinding). Для разработки есть `AGENT_SANDBOX_URL=local` — процессы на той же машине без изоляции, поэтому там каждый запуск по подтверждению. Всё, что код создаст в папке разговора, сразу видно и скачивается из чата.

```
agent-service ──(сеть sandbox)── sandbox-сервер ──docker.sock──▶ ak-sb-<сессия> ×N
                                                                 │ agent-sandbox-net (internal)
                                                                 ▼
                                                              egress ──▶ pypi.org, … (allowlist)
```
