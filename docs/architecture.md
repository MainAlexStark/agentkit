# Архитектура agentkit

## Два слоя

```
┌──────────────────────── проект (agentkit new) ────────────────────────┐
│ app/domain: prompt.md · tools.py · hooks.py · rules()                 │
│ app/skills · mcp.json · evals/ · deploy/*.env                         │
└───────────────────────────────▲───────────────────────────────────────┘
                                │ Domain
┌───────────────────────────────┴──────────── agentkit ─────────────────┐
│ server/   AgentService · build_app (API + веб-чат) · Auth · Settings  │
│ runs      RunManager (фон, SSE, один прогон на сессию) ── bus (Redis) │
│ scheduler cron из базы                                                │
│ agent     цикл ── llm/router ── openai_compat (OpenRouter, Yandex…)   │
│            │  ├── tools/registry ── builtin · domain · mcp            │
│            │  ├── permissions · hooks                                 │
│            │  ├── context (промпт, сжатие, обрезка) · skills          │
│            │  └── subagents (task → дочерний Agent)                   │
│ oauth     вход в MCP-серверы · attachments  файлы и картинки        │
│ projects  инструкции, файлы, память · devices + bridge.py  компьютер  │
│ sandbox   run_python / run_bash: контейнер на разговор · egress       │
│ store     SQLStore: SQLite / PostgreSQL                               │
│ evals · tracing · cli                                                 │
└───────────────────────────────────────────────────────────────────────┘
```

Правило границы: всё, что одинаково у любого агента, — в ядре; проект знает только свою предметную область. Улучшение ядра доезжает до всех проектов обновлением `vendor/agentkit` (`agentkit vendor`).

## Прогон

1. `POST /api/sessions/{id}/messages` → `RunManager.start` → фоновая задача → сразу `run_id`.
2. `Agent.run`: истекают висящие подтверждения → хук `user_prompt_submit` → сообщение в базу → `_loop`.
3. Шаг цикла: история (последняя сводка + хвост) → системный промпт → при переполнении сжатие → запрос к модели (стрим) → assistant в базу.
4. Нет вызовов → хук `stop` (может вернуть агента к работе) → `done`.
5. Есть вызовы → пачки: подряд идущие `parallel_ok` — одновременно. На каждый: есть ли инструмент → загружен ли (отложенный) → валидные ли аргументы → `pre_tool_use` → права → выполнение / отказ / карточка.
6. Есть карточки → прогон завершается со статусом `waiting_approval`. Решение человека (`POST /api/approvals/{id}`) — **новый прогон**: выполнить или отклонить, записать результат, и когда решены все карточки шага — продолжить цикл.

Почему подтверждение не ждёт в памяти: человек ответит через час с телефона, сервис за это время могут перезапустить. Состояние ожидания — строки в `ak_approvals`, а не корутина.

## События

Всё, что делает агент, — `Event` (`events.py`). Они пишутся в `ak_events` (кроме дельт текста), раздаются подписчикам SSE, уходят трейсерам. UI, evals и трейсы читают один и тот же поток. Курсор — `seq`; переподключение отдаёт пропущенное из базы и снимок недописанного текста.

## Качество: evals и replay

Журнал событий — общий источник для трёх вещей: чата, evals и разбора прогонов. `run_started` несёт текст запроса, поэтому прогон восстанавливается и из `ak_events`, и из JSONL трейсов, без таблицы сообщений.

* **Evals** (`evals.py`) гоняют того же агента, что едет в прод (`app.evals:make_agent` собирается через `assemble_agent`). Кейс — данные: рабочая папка до (`files`, с генераторами для длинных логов), разговор до (`history`, `memory`), ходы (`input`, `turns`, `answers`), права (`mode`, `approve`, `tool_policy`, `deny`), настройки (`config`, `max_steps`), и проверки — механические (`files` после, `tools_called`, `tool_args`, `contains`, `regex`, лимиты шагов, стоимости и ошибок) и судья. Судья зовётся только после механики: дешевле и не путает причины. Каждый кейс — своя in-memory база и своя папка, поэтому кейсы идут параллельно, по нескольким моделям и с повторами; сводка — доля успешных прогонов и pass^k (кейс прошёл во всех повторах), сравнение — по (набор, модель, кейс) с прошлым JSON.
* **Набор ядра** (`evals/harness`, агент `agentkit.bench`) проверяет только общее для любого агента. Его провалы — повод править ядро: в этой версии он нашёл потерю результата параллельного вызова в in-memory SQLite, пустую папку у субагента, «отклонил» без «не выполнено», которое модель читала как просьбу подтвердить, и голое «нет файла» без похожих имён.
* **Replay** (`replay.py`) собирает из событий прогоны и ходы (прогон по сообщению + продолжения после подтверждений), печатает ход и делает из хода два кейса: проводку (ответы модели из журнала — офлайн, ловит поломки ядра) и живой (та же задача модели, с критерием человека).

## Права

Решение принимает код, а не промпт (`permissions.py`, порядок — в docstring модуля). Источники: режим сессии, правила из окружения, выбор пользователя по инструменту (`tool_policy` в kv, у каждого свой; правила сервиса сильнее), зона агента (песочница — без вопросов), свойства инструмента (`read_only`, `destructive`, `needs_approval`), хук `pre_tool_use`. Субагент не может спросить человека: «спросить» для него — отказ, задача возвращается главному.

## Секреты — `redact.py`

Ключи и токены заменяются меткой `[секрет скрыт: <что>]` до того, как текст уйдёт модели или осядет где-то. Известные значения — секреты сервиса (переменные с KEY/TOKEN/SECRET/PASSWORD из окружения и настроек, пароли в `AGENT_DATABASE_URL`/`AGENT_REDIS_URL`, токены и заголовки MCP-серверов, токены OAuth по мере получения) — скрываются всегда. Шаблоны (sk-…, ghp_…, AKIA…, JWT, PEM, `PASSWORD=…`, пароль в URL) ловят чужие ключи в данных; выключаются `AGENT_REDACT_PATTERNS=false`. Значения-код (`api_key=settings.key`), числа, хэши и пути не трогаются — иначе `edit_file` не нашёл бы прочитанную строку.

Точки: результат инструмента в `Agent._invoke` — до модели, до обрезки и blob (с пояснением модели, только если что-то скрыто); каждое событие в `emit` — до базы, UI, SSE и трейсеров; стандартный `logging` — фабрикой записей (сообщение и traceback). Пишущий вызов с меткой в аргументах не выполняется ни в каком режиме: модель переписала бы .env или конфиг вместе с меткой вместо ключа — секрет вписывает человек. Сообщения человека в истории модели не меняются (ключ, который он сам дал агенту, нужен для дела), в журнале событий — скрыты.

## Контекст

Промпт — слоями, стабильное первым: правила ядра → промпт агента → правила хоста → skills → инструкции MCP → отложенные инструменты → окружение (дата без времени) → память. Сжатие режет только перед сообщением пользователя (пары вызов-результат не рвутся), сводку пишет модель роли small, исходная история остаётся в базе.

**Фоновая память** (`memory_auto.py`, `AgentConfig.auto_memory`): после хода со статусом done модель small получает реплики человека с прошлого прохода (курсор в kv `memory_cursor`) и текущую личную память и отвечает JSON `{add, update}`. Идёт после `run_finished` — человек уже видит ответ, а блокировка сессии ещё держится, так что два прохода по одним сообщениям не пересекутся; сообщение, отправленное в эти секунды, ждёт в очереди входящих. Всё важное — в коде, а не в промпте извлечения: результаты инструментов и вложения в запрос не попадают (документ «запомни, что…» — данные), запись только в `user:<id>` владельца разговора, исправлять можно только свои записи, удалять нельзя вовсе, лимиты на ход, маскирование и отбрасывание записей с маркером секрета. Ход, где агент сам вызвал `memory_save` / `memory_delete`, пропускается. Расход — событием `usage` с `memory: true`: входит в стоимость прогона и лимиты, но не в шаги.

**Смысловой поиск** (`semantic.py`): память и файлы проектов ищутся двумя способами сразу — по словам (tf-idf по грубым основам) и по смыслу (эмбеддинги, косинус), списки сливаются по местам (RRF): шкалы оценок несравнимы, места — сравнимы. Слова не выбрасываются: коды и номера (МИ 1592-2015, артикул) векторы находят хуже. Векторы — в той же базе, таблица `ak_vectors` (область, ref, кусок, хэш модели и текста): на PostgreSQL с pgvector — колонка `embedding vector` без размерности и частичный HNSW-индекс на каждую размерность (`WHERE dim = N`, поэтому модель меняется без миграции), иначе — float32 в `vec` и перебор в Python. Индекс догоняется лениво (`VectorIndex.sync` перед поиском сравнивает хэши — без изменений это один SELECT), поэтому его не нужно обновлять из каждого места, где меняется память; удаление и правка записи памяти или файла стирают её векторы сразу, в той же транзакции — «забудь» не оставляет текст в индексе. Модель эмбеддингов недоступна — поиск по словам, а не ошибка.

Память в промпте: пока помещается в `memory_inline_chars` — вся, как раньше, и `memory_search` модели не показывается. Не помещается — до двух третей места занимают записи, ближайшие к последнему сообщению человека (с отсечкой по косинусу от лучшей), остальное — самые новые; в промпте пометка «показано N из M — ищи через memory_search». Векторы запросов кэшируются: отбор повторяется на каждом шаге прогона с тем же вопросом, и промпт между шагами не меняется (кэш провайдера).

## Хранилище

`Store` — интерфейс; `SQLStore` — SQLAlchemy Core, таблицы `ak_*`, схема создаётся сама. Для встраивания в Django-проект можно реализовать `Store` поверх ORM хоста. Миграции (Alembic) — когда схема начнёт меняться у развёрнутых сервисов.

## Развёртывание

Стандарт MCP-серверов: сеть `mcp-network`, общий Caddy в `/opt/infrastructure`, блок по маркерам, секреты один раз, `./deploy.sh update` с автооткатом. Отличие — `flush_interval -1` в Caddy для SSE. Рядом с агентом поднимается Redis (только внутренняя сеть), по умолчанию 2 процесса uvicorn.

## Несколько процессов — `bus.py`

Всё долговременное — в базе (сообщения, события, подтверждения, очередь входящих, OAuth-токены), поэтому любой процесс может обслужить любой запрос. Шина (Redis; в одном процессе — `LocalBus` в памяти) нужна для того, чего в базе нет:

| Что | Как |
|---|---|
| «В сессии идёт прогон» | ключ `ak:run:<сессия>` с TTL 30 с, процесс продлевает его каждые 10 с; умер — ключ истёк сам |
| Живые события и куски текста | канал `ak:ev:<сессия>`; недописанный текст шага — `ak:partial:<сессия>` для подписавшихся посреди ответа |
| Отмена прогона в другом процессе | рассылка `{"cmd":"cancel"}`; владелец прогона ставит флаг отмены |
| «Перечитай MCP» после OAuth | рассылка `{"cmd":"reload"}` всем процессам; личные серверы и входы — `{"cmd":"reload_user","user":id}` |
| Обновление OAuth-токена | блокировка `ak:lock:oauth:<сервер>`: refresh ротируется, два одновременных обновления оставили бы процесс без токена |

Запуск по расписанию и решение по карточке защищены атомарным UPDATE в базе (`claim_schedule`, `claim_approval`), а не шиной: так они верны и без Redis.

## Сообщения на ходу

Если агент занят, новое сообщение ложится в `ak_inbox`. Цикл забирает очередь в начале каждого шага — там, где все вызовы предыдущего шага уже закрыты результатами, — и перед тем как закончить. Если прогон закончился раньше, чем сообщение легло в очередь, сервис запускает новый прогон сам (`RunManager.on_idle`). В UI такой пузырь помечен «агент прочтёт после текущего шага», пока не придёт событие `user_message`.

## Вложения — `attachments.py`

Файл — в `uploads/` рабочей папки сессии; в истории — только ссылка `{"type": "file", "path": …}`. Перед запросом к модели ссылка разворачивается: картинка — `image_url` (для моделей со зрением; большие уменьшены заранее), текст и извлечённый при загрузке текст PDF/DOCX/XLSX — в сообщение, длинное — началом и подсказкой `read_file`. Base64 в базе не хранится.

## OAuth для MCP — `oauth.py`

Порт `pkg/oauthclient` из OpenSeller. Admin жмёт «Подключить» → поиск метаданных → регистрация клиента (DCR) → экран согласия MCP-сервера → `/oauth/callback` → токены в `ak_kv` → все процессы перечитывают MCP. Пароль от MCP-сервера агент не видит. Владелец токена (`owner`): пусто — общий на сервер, подключает admin; id пользователя — свой вход у каждого. Запись — `ak_kv(ns="oauth", key="<сервер>@<id>")`, владелец берётся из одноразового state, а не из запроса callback: чужая ссылка согласия положит токен тому, кто её начал.

## Личные MCP-серверы

Реестр инструментов агента один на процесс, а личные серверы у каждого свои, поэтому они не добавляются в `agent.tools`. `Agent(user_tools=…)` — поставщик `(user) → UserTools`; на каждом шаге прогона `Agent.tools_for(user)` собирает реестр «общие + личные» (общий инструмент с тем же именем главнее) и кладёт его в `ToolContext.tools` — по нему работают вызов, подтверждение, `tool_search`, хуки и субагенты. Ядро о MCP при этом ничего не знает.

В сервисе `AgentService.user_mcp(user)` лениво держит на пользователя свой `MCPManager(owner=id)`: его личные серверы (kv `mcp_servers/<id>`) и общие с `personal_login`. Кэш сбрасывается рассылкой `{"cmd":"reload_user"}` во всех процессах (сохранил, вошёл, вышел), упавший сервер переподключается не чаще раза в 2 минуты, подключение ждёт не дольше 20 с.

Адрес личного сервера вводит не админ, а ходит по нему сервис изнутри своей сети. Поэтому `public_only`: только https, и `netguard.public_client` проверяет все адреса после резолва и подключается к проверенному IP (DNS-rebinding), без прокси из окружения. Через него же идут discover/DCR/token/отзыв OAuth — адреса из метаданных диктует сам сервер. Для разработки — `AGENT_USER_MCP_PRIVATE=true`.
## MCP-сервер хоста — `per_user`

Не путать с `personal_login`: там сервер общий, а OAuth-вход у каждого свой; здесь список инструментов и данные на пользователя отдаёт сам хост.


Хост (OpenSeller и т. п.) отдаёт агенту свои инструменты одним MCP-эндпоинтом с токеном сервиса. Каждый запрос несёт `X-Agent-User-Id` / `X-Agent-Roles` / `X-Agent-Session-Id`, вызов — ещё `X-Agent-Run-Id`; хост верит заголовкам только вместе с токеном. Список инструментов и инструкции (`initialize.instructions` — сведения о магазине, память хоста) берутся на каждый разговор: хост по сессии решает, что это за разговор (общий чат или работа над одним товаром, какой магазин), и отдаёт свои инструменты; `MCPManager.turn_context` — поставщик контекста, `TurnContext.tools` — инструменты хода. Цикл собирает на прогон реестр «общие + личные» (`Agent.tools_in(run_id)`): по нему идут вызов, `tool_search`, решение по карточке (это новый прогон — список берётся заново) и субагенты (через их фильтр `tools`/`deny_tools`). Личный инструмент не может подменить общий с тем же именем. Кэш — `per_user_ttl` (60 с); изменяющий вызов сбрасывает его сразу, как и любой вызов, в результате которого хост поставил `_meta["agentkit/refresh"]` (действие без подтверждения, поменявшее контекст: «запомни», «подключи сервис»), недоступный хост пробуется снова через 10 с и попадает в промпт текстом. Для изменений без подтверждения человека (агент карточки товара в OpenSeller) хост помечает инструмент `_meta["agentkit/concurrencySafe"]: false` — не параллельно с соседями, хоть он и «чтение» для прав, — а результат итогового инструмента — `_meta["agentkit/stop"]: "done"`: прогон заканчивается после этого шага (`ToolResult.stop`).

## Решения

| Решение | Почему |
|---|---|
| Python, FastAPI | EI_doc и большинство будущих агентов на Python; лучшая экосистема LLM. В Go-проекты агент встраивается сервисом по HTTP |
| Свой клиент OpenAI-совместимого API вместо SDK | у провайдеров «совместимость» неполная: reasoning, cost, cache_control, формат модели Яндекса — отличия видны полями конфига |
| Свой MCP-клиент вместо SDK | SDK 1.x → 2.x поменял API целиком, а нужна малая часть протокола |
| История в формате OpenAI | один формат для всех провайдеров, смена модели без миграции |
| Ядро в `vendor/` нового проекта | сборка на VPS не требует доступа к приватному репозиторию; обновление — одна команда |
| Своя система пользователей не встроена | у каждого продукта она уже есть; агент получает пользователя от хоста (сервисный токен + заголовки) |

## Проекты, компьютер, песочница

Ядро о них не знает напрямую: агент спрашивает у **поставщиков контекста** (`Agent.context_providers`) текст для промпта и какие инструменты спрятать на этом шаге (`TurnContext`). Проект подмешивает инструкции, память и файлы (или их оглавление); компьютер — какие папки открыты. Если компьютер не подключён или разговор не в проекте, их инструменты модели не показываются вовсе.

**Мост** (`bridge.py`) запускает человек у себя: он ходит на `/api/bridge/poll` (длинный опрос до 25 с) и получает команды из очереди шины (`Bus.push/pop`, в проде — Redis-списки), ответ возвращает в `/api/bridge/result`. Ключ ответа включает id устройства: чужой мост не подсунет результат. Какие папки открыты и разрешены ли команды, решает только мост — сервер не может расширить доступ.

**Папки проекта**: человек привязывает к проекту свои открытые в мосте папки (ключ `<проект>:<пользователь>` в `ak_kv`, по пути — имя папки мост выдаёт заново). В разговоре такого проекта `device_tools` пускают только в них: корень пути сверяется до отправки команды, пустой путь у `pc_list`/`pc_search` и `cwd` у `pc_run` подменяются папками проекта. Сам `pc_run` папкой не ограничить — это отдельное разрешение моста с подтверждением каждой команды. Привязка доступ не расширяет: закрытая на компьютере папка остаётся недоступной.

**Компьютер агента** (`agentkit.sandbox`) — `run_python` / `run_bash` вне процесса сервиса. Сервер песочницы — единственный, кто держит `docker.sock`; на каждый разговор он создаёт свой контейнер (`ak-sb-<сессия>`): uid 1000, `cap_drop: ALL`, только чтение корня, `--init`, лимиты памяти/CPU/процессов, смонтирована только папка этого разговора (`/work`). Контейнер живёт, пока разговор активен (фоновые задачи `background=true`, логи в `.jobs/`), и удаляется после простоя (`SANDBOX_IMAGE`, `SANDBOX_IDLE_MINUTES`); пакеты `pip install` ставятся в `/work/.home` и переживают пересоздание. У каждого разговора своя сеть `ak-sbn-<сессия>` (internal, своя /28 из `SANDBOX_SUBNET_POOL`): в ней только его контейнер и egress, ни сервиса агента, ни базы, ни соседних разговоров. `run_python` выполняется в **ядре** (`agentkit.kernel`) — процессе Python на unix-сокете в контейнере разговора: переменные живут между вызовами, зависшая ячейка убивается вместе с ядром, и вывод говорит, что состояние сброшено. Единственный путь в интернет — прокси **egress** (`agentkit.egress`): домены из `AGENT_SANDBOX_EGRESS`, внутренние адреса запрещены всегда, IP проверяется после резолва и соединение идёт на тот же IP (без DNS-rebinding). Для разработки есть `AGENT_SANDBOX_URL=local` — процессы на той же машине без изоляции, поэтому там каждый запуск по подтверждению. Всё, что код создаст в папке разговора, сразу видно и скачивается из чата.

**Превью**: агент поднимает сервер в контейнере (`run_bash background=true`, хост 0.0.0.0) и вызывает `sandbox_preview(port)`; человек получает подписанную ссылку `/sandbox/p/<подпись>/` (разговор, порт, срок — HMAC, секрет в базе). Сервис ходит к контейнеру через обратный порт egress (3129, токен песочницы, цель только `ak-sb-*`). Страница отдаётся с `Content-Security-Policy: sandbox` без `allow-same-origin`: её JS не прочитает токен чата из localStorage, а куки и Authorization человека наверх не уходят.

```
agent-service ──(сеть sandbox)── sandbox-сервер ──docker.sock──▶ ak-sb-<сессия> ×N
      │                                                          │ ak-sbn-<сессия> (internal, своя)
      └─ превью ──▶ egress:3129 ─────────────────────────────────┤
                    egress:3128 ◀── HTTP(S)_PROXY ───────────────┘
                       └──▶ pypi.org, … (allowlist)
```
